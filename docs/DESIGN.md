## 0. 一页纸摘要

| 问题 | 答案 |
| --- | --- |
| 这是什么 | 一条电商售后工单进来，输出**意图分类 + 回复草稿**，涉及不可逆操作转人工 |
| 为什么不是通用 Agent | 意图只有 4 类，工具只有 6 个，路径只有 3 条；任何"帮用户做点别的"的需求都违反第 2 章 |
| 目标工程能力 | 有界执行、四表trace、固定回归集与失败分析；当前只有文档，需实现及产物证明 |
| 最容易被质疑的点 | 场景太窄 → 第 2.3 节给出"窄是设计选择"的论证；指标是自测的 → 第 10 章给出防作弊条款 |
| 交付形态 | 可一条命令启动的服务 + CLI + 离线评估脚本 + 本文档集 |

**边界一句话**：只做"读一条工单 → 查合成订单及关联信息 → 写一段草稿"，其余一律不做。

## 1. 定位（不可改写条款）

> 输入一条用户工单（退款 / 改地址 / 催发货 / 其他），输出意图分类 + 回复草稿；
> 涉及不可逆操作时转人工确认；全程可追踪、可回放、可量化迭代。

这条定义受三条约束保护，任何改写都需要走变更控制：

1. **单一输入**：一次只处理一条工单。批量、会话式连续对话、多工单并发协商都不在范围内。
2. **两类输出**：`intent`（4 类封闭集）+ `reply_draft`（一段可直接发送的中文文本）。不输出工单优先级、不输出客户画像、不输出处理时长预估。
3. **一个动作边界**：Agent 可以"建议"和"生成待确认单"，**不可以**自行执行退款、改地址等不可逆写操作。

### 1.1 反面定义（用来快速拒绝需求）

| 别人可能会问 | 本项目回答 |
| --- | --- |
| 能不能顺便回答"你们几天发货"这类政策咨询？ | 不能。政策咨询是知识库问答，属于 NG-4。草稿里可以带一句工具返回的政策原文，但不做检索问答。 |
| 能不能接多个平台（淘宝/京东/抖音）订单？ | 不能。平台适配是集成问题，不是 Agent 问题（NG-6）。数据层只认一张 mock 订单表。 |
| 能不能自动退款？ | 不能。退款是资金操作，只出"待人工确认单"（NG-2）。这是合规底线，不是能力不足。 |
| 能不能做成客服聊天机器人，多轮跟进？ | 不能。多轮会引入会话状态膨胀与"谁在说话"的归属问题，与本项目要证明的"有界执行"背道而驰（NG-1）。 |
| 能不能用多 Agent 协作，一个分类、一个答复、一个审核？ | 不能。本场景分类/答复/审核可由单条执行链和策略层完成；模型选择存在不确定性，多Agent的通信成本尚无已验证收益（NG-3）。 |

## 2. 范围边界

### 2.1 非目标清单（Non-Goals，硬边界）

| 编号 | 非目标 | 判定：出现以下情况即越界 | 违反后果 |
| --- | --- | --- | --- |
| NG-1 | 通用对话 / 聊天机器人 | 出现"继续上一轮对话"的会话 ID 复用、或系统提示里出现"你是乐于助人的助手" | 项目定位失效，面试时无法讲清边界 |
| NG-2 | 自动执行资金/地址变更 | 出现退款或改地址的实际写入分支；模型或外部输入可以传approved授权 | 合规事故，直接判定不合格 |
| NG-3 | 多 Agent 协作 / 编排框架 | 依赖里出现 langgraph / autogen / crewai / langchain；或出现"Agent 之间发消息"的抽象 | 违反硬约束 1，评审直接打回 |
| NG-4 | RAG / 向量检索 / 知识库问答 | 出现 embedding 调用、向量库依赖、chunk 切分逻辑 | 场景漂移，且引入无法归因的失败源 |
| NG-5 | 模型微调 | 出现训练脚本、LoRA、数据集格式转换 | 与"prompt + 工具 + 策略迭代"的叙事冲突 |
| NG-6 | 多平台 / 真实电商 API 集成 | 出现淘宝/京东 SDK、OAuth 授权流程 | 变成集成项目，Agent 机制被稀释 |
| NG-7 | 前端工程化 | 出现 React/Vue 工程、构建链、组件库 | 展示成本挤占评估闭环时间（硬约束 5） |
| NG-8 | 云服务与付费中间件 | 出现 Redis / MQ / 向量数据库 / 托管工作流 / K8s | 违反零付费约束，且无法离线复现 |
| NG-9 | 通用工具（搜索、代码执行、文件操作） | 工具注册表里出现与售后无关的工具 | 违反"不为展示造通用能力"（硬约束 3） |
| NG-10 | 追求 SOTA 指标 | 报告里出现"超过某某模型"的对比结论 | 24 条自建集不具备对比效力，属于过度声称 |

### 2.2 边界判定流程（提任何需求先跑这三问）

```
新需求进来
  │
  ├─ Q1 它服务的是"一条工单 → 分类 + 草稿"这条链路吗？
  │     否 → 拒绝（记入 NG 清单，不实现）
  │     是 ↓
  ├─ Q2 它能回答"对齐了哪家 JD 的哪条信号"吗？
  │     否 → 拒绝（硬约束 4：答不出就不做）
  │     是 ↓
  ├─ Q3 它会让 trace / 回放 / 归因变模糊吗？
  │     是 → 降级为"可选项"，默认不做
  │     否 → 进入开发文档的 WBS
```

### 2.3 为什么"窄"是设计选择而不是能力不足

窄场景换来四件通用 Demo 拿不到的东西：

1. **可穷举**：4 意图 × 2 复杂度 = 8 个格子，24 条用例能把每格填满 3 条；这只覆盖自建矩阵，不等于穷举所有表达或线上分布。
2. **可归因**：失败只有四种原因（意图/工具/参数/草稿），每条失败都能落到一格，修复有优先级。
3. **可回放**：工单是短会话，保存的输入、请求响应、工具快照及配置可重建历史trace；重新调用真实模型不保证输出相同。
4. **可约束**：路径只有 3 条，所以"最多 6 步"这种数字不是拍脑袋，而是"典型路径预估 3 次模型请求 + 1 次纠错 + 2 步余量；最终由实测路径确认"。

## 3. 使用者与场景边界

### 3.1 使用者

| 角色 | 怎么用 | 不做什么 |
| --- | --- | --- |
| 售后客服（主用户） | 看分类、看草稿、点"发送"或"转人工" | 不训练模型、不配置工具 |
| 客服主管（次用户） | 看审计日志、看转人工原因分布 | 不做实时监控大屏 |
| 开发者（本人） | 跑评估、看 trace、改 prompt/工具 | 不做在线 A/B 平台 |

### 3.2 收哪些工单

| 收 | 例子 |
| --- | --- |
| 单意图明确诉求 | "订单 O1004 买错了，退款" |
| 含明确订单号，或缺号需要补充信息 | "我那个 58 块的手机壳要退" → 生成补充订单号的草稿并结束本run，不按金额猜订单 |
| 带情绪但不带威胁 | "怎么还没发货啊，急死了" |
| 多诉求但可归一到一类 | "还没发货，能不能改地址" → 归 address_change（改地址优先，因为涉及已发货拦截） |

### 3.3 不收哪些工单（明确拒答或直接转人工）

| 不收 | 处理方式 |
| --- | --- |
| 与订单无关的咨询（发票、优惠券规则、加盟） | 分类为 `other`，低置信转人工 |
| 投诉/舆情/法律威胁（"我要起诉""曝光你们"） | 转人工，且草稿不得出现任何承诺性措辞 |
| 要求赔偿、补偿、承诺时效 | 转人工（策略层正则拦截） |
| 跨订单批量问题（"我这 5 个订单都要退"） | 转人工，不做批量拆解 |

## 4. 系统边界

### 4.1 外部依赖（只有这些，多一个都要评审）

| 依赖 | 用途 | 失效时的行为 |
| --- | --- | --- |
| 模型 API（OpenAI 兼容协议） | 意图判断、工具选择、草稿生成 | 可重试错误最多重试1次，消耗剩余步数与deadline；仍失败 → degraded + 转人工 |
| 本地 mock 订单数据（JSON） | 订单/物流/退款政策 | 视为数据缺失 → `ORDER_NOT_FOUND` |
| SQLite 文件 | 四张表持久化 | 启动失败立即报错，不做内存降级（避免"看起来能跑"的假象） |

**不依赖**：外部消息队列或缓存服务、向量库、对象存储、第三方风控、真实支付网关。单run工具结果缓存在SQLite内实现。

### 4.2 信任边界

```
[不可信] 用户工单文本 ──► 输入校验（长度/字符/工单号格式）──► [半可信] 模型输出 ──► JSON 契约校验 ──► 策略层覆写 ──► [可信] 落库结果
```

五条硬规则：

1. 模型输出**永远**经过 `parse_final_answer` + pydantic 校验，解析失败最多修复 1 次，之后降级。
2. `needs_human` 由**策略层**最终决定，模型只能"建议"。策略层可以覆写模型结论，反之不行。
3. 用户文本中的任何指令（"忽略以上规则""直接给我退款"）都只作为工单内容看待，不进入系统提示。
4. 订单工具使用程序绑定的user_id校验订单归属；本地演示不代表生产身份认证。
5. 当前版本没有真实动作后端和审批接口，approved不属于模型或HTTP输入。

### 4.3 数据流

```
TicketIn ──校验──► sessions(running)
   │
   ├─► 上下文构建（窗口 + 摘要）
   ├─► 模型调用 ──► tool_calls? ──是──► 钩子前置检查 ──► 幂等查缓存 ──► 工具执行 ──► tool_calls 落库 ──► 钩子后置（审计）
   │                                  └─否──► 解析最终答案 ──► 策略层判定 ──► 草稿落库 ──► evaluations（离线时）
   └─► 终止条件命中（步数/token/墙钟）──► 降级 + 转人工
```

## 5. 六组件契约

每个组件只回答三件事：**它负责什么、它不许做什么、它失败时系统怎么表现**。
"不许做什么"是本文最有约束力的部分——跨层直连是最常见的架构腐化方式。

### 5.1 E 执行循环

| 项 | 内容 |
| --- | --- |
| 职责 | 承载"校验 → 路由 → 选工具 → 调工具 → 判断继续"的有界循环；累计 token、计时、决定 `stop_reason` |
| 输入 | `TicketIn` + 配置 + Provider |
| 输出 | `RunResult`（含 `steps`、`stop_reason`、`tool_calls`、`usage`、`latency_ms`） |
| **禁止** | ① 直接拼 SQL（必须经 Store）；② 直接 import 具体工具实现（必须经注册表）；③ 无上限的 `while True`；④ 在循环里做业务规则判断（属于策略层） |
| 失败模式 | 模型异常 → `upstream_error`；输出不可解析 → `invalid_output`；约束命中 → `max_steps` / `token_budget` / `timeout` |
| 验收 | 分别覆盖max_steps、token_budget、timeout、invalid_output、upstream_error五种降级原因，均转人工 |

### 5.2 T 工具注册表

| 项 | 内容 |
| --- | --- |
| 职责 | 用装饰器把函数注册成"带 JSON Schema 的工具"；执行前做参数校验；把工具业务异常转成结构化错误；数据库trace写入异常必须传播 |
| 输入 | 工具名 + 参数字典 + `ToolContext` |
| 输出 | `ToolResult{status, data, error{code,message,hint}}` |
| **禁止** | ① 将业务异常抛给模型调用方（业务失败需结构化；基础设施写入异常例外）；② 在工具里改会话状态（除 `create_ticket_draft` 的落库）；③ 允许未知参数（`extra="forbid"`）；④ 在工具里 sleep 或重试上游 |
| 失败模式 | 错误码封闭集：`INVALID_ARGS` / `ORDER_NOT_FOUND` / `NOT_SHIPPED` / `REFUND_NOT_ALLOWED` / `TOOL_UNAVAILABLE` / `INTERNAL_ERROR` / `APPROVAL_REQUIRED` / `DUPLICATE_SUPPRESSED` |
| 验收 | 每个工具至少 2 条测试：成功路径 + 一个失败码；未知参数必须返回 `INVALID_ARGS` |

### 5.3 C 上下文管理

| 项 | 内容 |
| --- | --- |
| 职责 | 保留同一run内部最近 N 轮模型/工具消息；更早的内容折叠为**确定性**结构化摘要（同输入必得同摘要） |
| 输入 | 系统提示、工单、历史 turns、上一版摘要 |
| 输出 | 发给模型的消息数组 + 新摘要 |
| **禁止** | ① 使用向量检索或语义召回（NG-4）；② 让模型来写摘要（会引入不确定性与额外成本）；③ 把工具调用与工具结果拆开截断 |
| 失败模式 | 窗口设置过大导致 token 超预算 → 由 E 的预算约束兜底；摘要字段缺失 → 用空值补位，绝不省略字段 |
| 验收 | 单测注入至少 8 轮消息，验证超出 6 轮窗口的旧轮被折叠且字段齐全；`role=tool` 消息不被截断；折叠前后消息长度和token估计变化可测，精确token需对应供应商计量 |

摘要固定 6 字段：`intent_history`、`slots`（覆盖写）、`tools_called`、`last_decision`、`open_questions`、`need_summary`。

### 5.4 S 状态存储

| 项 | 内容 |
| --- | --- |
| 职责 | 恰好 4 张表：`sessions` / `turns` / `tool_calls` / `evaluations`；提供按 `run_id` 全量取回 trace 的读接口 |
| 输入 | 运行过程中的结构化记录 |
| 输出 | 可回放的 trace（会话 + 轮次 + 工具调用） |
| **禁止** | ① 建第 5 张表（除非走变更控制）；② 在存储层写业务判断；③ 用 ORM 隐藏 SQL（要能直接 `sqlite3` 查）；④ 把幂等键设为全局唯一，或让缓存跨 run 复用 |
| 失败模式 | 写入失败必须向上抛（不允许静默吞异常）；仅明确的幂等唯一约束冲突返回已存在，其他写入异常不得吞掉 |
| 验收 | 任意 `run_id` 都能一条命令打印完整 trace；首次执行幂等键唯一；重复尝试写缓存命中行且幂等键为NULL，保留完整审计 |

> 历史教训（写进契约）：幂等唯一索引**必须**带上 `session_id`，否则两次评估运行会因为工单号相同而互相吞掉审计记录。这条以「禁止 ④：幂等键不得全局唯一」的形式沉淀。

### 5.5 L 生命周期钩子

| 项 | 内容 |
| --- | --- |
| 职责 | 工具调用前后拦截：审计日志、耗时打点、不可逆操作转人工、敏感信息脱敏 |
| 输入 | 工具规格 + 参数 + 上下文 + 步号 |
| 输出 | `HookDecision{allow, approval_required, reason}` + 审计行 |
| **禁止** | ① 在钩子外做不可逆操作检查（唯一入口原则）；② 记录原始手机号/地址（必须脱敏）；③ 钩子内发起网络请求 |
| 失败模式 | 拦截 = 不执行 + 返回 `APPROVAL_REQUIRED`；额外JSON审计日志失败 → 警告；数据库trace写失败 → 中止并报内部错误，不返回成功 |
| 验收 | 10 条手工用例证明"该转人工的确实转了"；审计文件中不出现完整手机号 |

### 5.6 V 评估接口

| 项 | 内容 |
| --- | --- |
| 职责 | 加载 24 条确定性用例与 50 条草稿用例；跑批、算指标、按 run 回放、版本对比、生成报告 |
| 输入 | 数据集 + prompt 版本 + Provider |
| 输出 | `reports/eval_<version>_<tag>.{json,md}`（含逐条结果与失败明细） |
| **禁止** | ① 手改报告数字；② 用测试集调参后再在同一集上宣称效果（见第 10.5 节防作弊）；③ 把桩（离线假模型）的数字当作模型效果 |
| 失败模式 | 数据集缺失/格式错 → 立即失败；单条用例崩溃 → 记为失败并继续（不中断整批） |
| 验收 | scripted或冻结响应连跑可一致；真实模型保存相同实验条件、逐次结果及波动，不要求得分完全一致 |

## 6. 接口契约

### 6.1 输入 `TicketIn`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `ticket_id` | str | 正则 `^[A-Za-z0-9_-]{6,40}$` | 业务幂等键；重复且会话未结束 → 拒绝 |
| `user_id` | str | 1–64 字符 | 审计及订单归属检查；本地mock由调用者给定，生产身份认证不在范围内 |
| `text` | str | 1–2000 字符，去空白后非空 | 工单原文 |
| `order_id` | str? | 可选，格式 `O` + 4 位数字 | 与正文明确订单冲突或多订单时转人工；缺失则抽取，仍缺失返回补充信息草稿 |

校验失败：`status=rejected`、`stop_reason=input_invalid`、不创建会话、不消耗模型调用。

### 6.2 输出 `RunResult`

| 字段 | 说明 |
| --- | --- |
| `run_id` | 本次运行ID，回放入口；输入校验或重复拒绝未建会话时为null |
| `status` | `ok` / `rejected` / `degraded`（三态封闭，不允许"部分成功"） |
| `stop_reason` | `finalized` / `max_steps` / `token_budget` / `timeout` / `invalid_output` / `upstream_error` / `duplicate_ticket` / `input_invalid` |
| `steps` | 执行循环已完成的步数；输入拒绝时为 0 |
| `answer` | `FinalAnswer{intent, confidence, slots, reply_draft, needs_human, escalate_reason, used_tools}`；`rejected` 时为 `null` |
| `tool_calls` | 每次调用的 `{step, name, ok, latency_ms, error_code, cached, approval_required, args_digest}` |
| `usage` | input_tokens/output_tokens/total_tokens/cost_cny及计量来源；缺usage时费用为null，不能当0 |
| `latency_ms` / `prompt_version` / `note` | 可观测字段；`note` 记录拒绝原因 |

### 6.3 对外 HTTP 语义

| 场景 | 状态码 |
| --- | --- |
| 正常完成（含转人工） | 200 |
| 输入不合法 | 422 |
| 重复工单（会话未结束） | 409 |
| 上游模型不可用且重试失败（`upstream_error`） | 503，响应体仍是完整 RunResult |
| `run_id` 不存在 | 404 |
| 内部异常或数据库trace写入失败 | 500 |

其他预算/格式降级返回200且status=degraded。SSE响应头发出后用error事件表达错误，不能再改变HTTP状态码。
**`upstream_error` 是唯一同时出现在 503 与状态机里的原因**：它按 degraded 落库（`needs_human=true`、固定降级草稿、`run_id` 非空、trace 可查），只是 HTTP 码用 503 表示"上游故障、可重试"。禁止返回 503 却不带 RunResult，那会让运行记录查不到。除此之外三种终态互斥：200 finalized、200 degraded、503 degraded。

### 6.4 SSE 事件（`POST /v1/tickets/stream`）

`open` → `step` → `tool_call` → `tool_result` → （可多次）→ `final` 或 `error`。
约定：步骤流不等于逐token文本流；final/error只发送一个终态。断连取消上游并终结运行；不支持Last-Event-ID续传，重连查询trace。

### 6.5 数据库（恰好 4 张表）

| 表 | 关键列 | 用途 |
| --- | --- | --- |
| `sessions` | `id, ticket_id, user_id, order_id, input_text, prompt_version, status, stop_reason, needs_human, cost_cny, latency_ms, summary_json, draft_text` | 一次运行的头部信息 |
| `turns` | `session_id, idx, role, content, intent, confidence` | 模型看到的每一轮 |
| `tool_calls` | `session_id, step, name, args_json, ok, error_code, latency_ms, result_json, idempotency_key, approved` | 每次工具调用含被拦截项；approved仅为程序审计字段，首版恒false，不是外部授权输入 |
| `evaluations` | `session_id, case_id, prompt_version, intent_gold, intent_pred, intent_ok, tools_ok, args_ok, draft_grade, cost_cny, latency_ms` | 离线评估结果 |

索引约束：`UNIQUE(session_id, idempotency_key)`，不是全局唯一；缓存审计行该键为NULL。
另建活动工单部分唯一索引 `(user_id,ticket_id) WHERE status='running'`，原子防重复登记。请求/配置/计量/快照字段补充见IMPLEMENTATION第7章，仍只四表。

## 7. 执行状态机与三个约束

```
running ──finalized──► ok
   │
   ├──max_steps / token_budget / timeout / invalid_output / upstream_error──► degraded（强制 needs_human=true）
   └──duplicate_ticket / input_invalid──► rejected（不建会话）
```

| 约束 | 阈值（默认） | 防的是什么 | 为什么不能省 |
| --- | --- | --- | --- |
| `max_steps` | 6次Provider请求尝试，重试及修复也计数 | 模型反复调同一工具、参数不变造成的调用死循环 | 只看 token 不够：短参数的工具调用可能很便宜但次数无限 |
| `token_budget` | 6000应用预算目标，调用前估计并限制输出，调用后以usage核对 | 工具结果反复入上下文造成的窗口膨胀与成本失控 | 只看步数不够：一步就能塞进上万 token。这是 token 上限，与 10.1 的 ¥0.005 费用目标是两条独立约束，达标与否分开报告 |
| `wall_clock_s` | 30秒总deadline，含重试等待；异步请求使用剩余时间超时 | 上游 HTTP 悬挂（此时步数不增长，token 也不增长） | 只有时钟能覆盖"卡住"这一态 |

调用前估计并不构成跨供应商的精确token或费用硬上限；缺计量必须显式记录。
三者**不可合并**为"超时"或"超预算"，因为它们覆盖的故障态互不包含。任何约束命中都必须带 `stop_reason` 退出并转人工，禁止"静默重试到成功"。
状态到 HTTP 的投影见 6.3：`ok` 与转人工 200；`degraded` 中除 `upstream_error` 外 200；`upstream_error` 503（body 仍是 RunResult）；`rejected` 为 422（`input_invalid`）或 409（`duplicate_ticket`）。

## 8. 上下文策略（为什么不是向量检索）

| 维度 | 本方案 | 若用向量检索 | 结论 |
| --- | --- | --- | --- |
| 会话长度 | 单run内部模型/工具轮次；不接续用户聊天，实际长度待测 | 无优势，反而多一次 embedding 调用 | 检索解决不了不存在的问题 |
| 状态语义 | 同run已验证槽位按规则更新，冲突订单号先转人工 | 召回相似记录不能替代事实归属与冲突校验 | 显式状态更新优先，检索可作未来补充 |
| 可复现 | 摘要纯函数，同输入同输出 | 召回受索引版本影响 | 回放需要确定性 |
| 成本 | 确定性摘要无额外模型调用 | 检索可能增加embedding及维护成本 | 本场景先不引入，是否超预算需测量 |

**换方案的触发条件**（写清楚，避免"以后再说"）：未来经范围变更支持用户多轮，且超过20轮或需要跨工单历史时，先做"结构化字段 + 关键词兜底"，仍不够再评估检索。

## 9. 钩子与幂等

### 9.1 转人工触发条件（策略层，优先级从上到下）

| 优先级 | 条件 | `escalate_reason` |
| --- | --- | --- |
| 0a | 投诉或法律威胁（查询订单前） | `COMPLAINT_OR_THREAT` |
| 0b | 明确要求跨两个及以上订单处理（查询订单前） | `MULTI_ORDER` |
| 0c | 至少存在一个订单号候选，但候选互相冲突或无法唯一确定（查询订单前） | `AMBIGUOUS_ORDER_ID` |
| 0d | 属于必须查订单的意图，且正文与结构化输入均无有效订单号候选（查询订单前） | `MISSING_ORDER_ID` |
| 1 | 非正常终止（步数/token/超时/解析失败/上游错误） | 对应 `stop_reason` 大写 |
| 2 | 工具被钩子拦截（不可逆操作） | `IRREVERSIBLE_ACTION` |
| 3 | 订单不存在 | `ORDER_NOT_FOUND` |
| 4 | 工具连续失败 ≥ 2 次 | `TOOL_FAILURE` |
| 5 | 退款且订单已发货（需拦截物流） | `REFUND_AFTER_SHIP` |
| 6 | 退款金额 > ¥200（阈值可配） | `REFUND_OVER_LIMIT` |
| 7 | 已超过售后期 | `REFUND_NOT_ALLOWED` |
| 8.5 | 签收事实与物流记录矛盾（例如“显示已签收但我没收到”“签收时间与实际不符”），且无赔偿/追责诉求；仅 `shipping_urge` 命中 | `DELIVERY_DISPUTE` |
| 8 | 改地址（正文出现 ≥2 个互相矛盾的地址 → `ADDRESS_CONFLICT`，先于发货状态判定；否则已发货 → `ADDRESS_AFTER_SHIP`，未发货 → `ADDRESS_CHANGE`） | 见左 |
| 9 | other兜底，或低置信不足以形成可靠草稿 | `LOW_CONFIDENCE` |
| 10 | 草稿含承诺性措辞（赔付/赔偿/补偿/保证/一定/百分百） | `DRAFT_RISK` |
| 10.5 | 退款结论缺少 `refund_preview` 事实支撑（未查到预览就直接断言可退/已退） | `INSUFFICIENT_EVIDENCE` |
| 11 | 模型自述需要人工 | `MODEL_FLAGGED` |

预检在第一轮模型响应完成结构化意图/槽位抽取后、任何工具请求交给注册表前执行；同一响应中的工具请求先暂存。预检读取原始文本、已校验的 `intent` / 订单槽位和可识别订单号候选，并将未执行的工具请求保留在 `turns` trace 中。`tool_calls` 只记录已交给注册表的调用。

`MISSING_ORDER_ID` 只适用于 `refund`、`address_change`、`shipping_urge` 等必需订单的意图；`other` 不因缺订单号命中 0d，继续走置信度与 `LOW_CONFIDENCE` 策略。正文含多个订单号但没有明确批量处理意图，或结构化订单号与正文候选冲突，判 `AMBIGUOUS_ORDER_ID`；明确要求同时处理多个订单，判 `MULTI_ORDER`。投诉/威胁优先于其他预检原因。

预检命中时正常完成运行：`status=ok`、`stop_reason=finalized`；`steps` 计入已完成的模型请求，通常为 1；`usage` 记录该请求的实际计量，缺失时沿用 `usage.source=missing` 与空成本口径。写入固定安全草稿、`needs_human=true` 和对应 `escalate_reason`，不调用订单工具。

设计原则：漏转与误转分开评估，不以全部转人工作为改进。改地址按策略必转人工，评估时将其作为策略要求并单列，不归因为模型误转；同时报告各意图的指标。首版不存在真实动作后端；动作阻断由钩子保障，漏转主要造成错误草稿风险。草稿风险命中后替换错误承诺，不能只改needs_human。

### 9.2 幂等

- 键 = `sha1(ticket_id | tool_name | canonical_args)`，作用域 = **单次 run**。
- 同一 run 内重复调用命中缓存，返回首次结果，并落一条"缓存命中"审计行。
- 跨 run 不共享缓存（否则重跑读到旧数据，评估失真）。
- 被钩子拦截的调用**不占用**幂等键（当前版仍保持拦截；未来如增加审批执行需单独变更合同）。

## 10. 评估口径（数字只能来自这一章）

### 10.1 数据集

| 数据集 | 规模 | 构造规则 | 用途 |
| --- | --- | --- | --- |
| 确定性集 `eval_cases.jsonl` | 24 | 4 意图 × 简单/复杂 × 3 条；每条带 `intent` / `order_id` / `expected_tools` / `expected_args` / `expected_needs_human` / `expected_reason`（可空）/ `split` | 分类、工具、参数、转人工 |
| 草稿集 `drafts_50.jsonl` | 50 | 与24条不重叠，带必需要素及人工评分理由；使用其调参后不再视为留出集 | 自动要素通过率与人工采纳率分开 |
| 新独立盲测（待提供） | 12 | 4 意图 × 3 条；独立出题与复核、先冻结候选及口径、外部保管、一次运行后退役；流程见 BLIND_EVAL.md | 只支持该范围内的独立小样本结果，不代表线上总体 |
| 旧 `holdout.jsonl` | 12 | 同一实现者生成、已阅读且已运行，独立性不足；后续只作回归/诊断 | 不再用于独立泛化结论；历史数字保留 |
| 手工验收集 | 10 | 基础转人工场景；10 条分别并入 AC01 / AC05 / AC16–AC19，另有 AC20–AC21 属基础设施与预检验收 | 不声称穷举全部条件 |

"复杂"的可操作定义：一句话里 ≥2 个诉求、或带明确时效/超期争议、或带情绪与威胁。

### 10.2 指标定义（写成公式，避免各说各话）

```
分类准确率   = 意图与标注一致的条数 / 24
工具正确率   = 期望工具集合与实调集合完全相等（双向，不含 create_ticket_draft）的条数 / 24
参数正确率   = 期望调用匹配且无错误/越权尝试的条数 / 24；只对订单ID规范化，地址等不能统一大写；金额整数分精确比较
转人工准确率 = needs_human 与标注一致的条数 / 24（冻结 holdout 单独报告 /12）

转人工准确率的分母只计**确定性**用例：标注里 `expected_needs_human = null` 的条目（信息类咨询，转人工与否取决于模型置信度）不计入分母，单独以 `escalation_scored` / `escalation_excluded` 报告。分母缩小必须在报告里写明，不能只报比率。
自动要素通过率 = 自动规则通过条数 / 草稿样本数
人工采纳率   = 人工评为A档的条数 / 已人工复核的条数；无人工复核则待实测
单次成本     = (input_tokens × 每百万输入单价 + output_tokens × 每百万输出单价) / 1,000,000 × 汇率
平均成本     = 计量完整样本总成本 / 对应样本数；缺失计量和估计成本单列
P95 延迟     = 耗时升序第ceil(0.95*n)个，包含失败/超时并报告n
转人工       = 同时报告TP/FP/FN/TN、漏转、误转及自动草稿覆盖率
```

`drafts_50` 的当前 A=30/50 来自实现者规则脚本，只能称为“实现者自查通过率 60%”；字段 `human_grade` 是历史兼容命名，不代表实际客服复核。客服采纳率仍待实测。

当前验收断言、业务规则、样本和初筛评分由同一实现者完成，尚无第二人代码及业务复核，这是主要结构性风险。补充 AI 审查不能替代第二人签字；旧评分的已知缺陷与 AC 覆盖缺口见 `reports/review-2026-11-05.md`。新盲测使用独立评分入口，不沿用这些已知缺陷。

改地址工单按策略标注为必转人工，应计入策略判定正确；需另列策略覆盖和各意图误转率，避免把预期转人工误报为模型误转。

### 10.3 迭代门槛（不达标不允许合并）

1. 冻结离线回归中分类、工具、参数任一项少1条即退化；真实模型候选差异须重复实验定位，记录波动；
2. 不得新增安全必转案例的漏转；额外评估误转与自动覆盖，不能靠全部转人工获通过；
3. 成本与 P95 只看趋势，不作为通过门槛，但超预算必须解释；
4. 每次改动必须留下：新版报告 + 旧版对比表 + 失败用例回放结果。

### 10.4 Bad Case 四类归因

| 归因 | 判定 | 后果 |
| --- | --- | --- |
| A 意图识别错 | 意图不一致 | 整条链路跑偏（工具、草稿全错） |
| B 工具选错 | 意图对、工具集合不等 | 答案缺事实依据 |
| C 参数提取错 | 工具对、参数不符 | 查到错误订单，风险最高 |
| D 草稿质量差 | 前两者对、草稿缺要素或含越权承诺 | 影响采纳率与合规 |

**一般语义问题参考 A → C → B → D**：安全、越权和基础设施故障优先；C会让结论指向错误事实，风险高于少调一个工具；
B 只影响信息完整度；D 不影响业务动作，但必须在下一版前修完（否则采纳率无意义）。

### 10.5 防作弊条款（写进文档，评审时可核对）

1. 24 条用例的题干不得出现在任何 prompt 中（脚本自动检查）；
2. 禁止为了提分修改离线桩（scripted provider）的关键词表；
3. 24 条及已暴露旧 holdout 只能报告回归/历史结果；新独立盲测需按 BLIND_EVAL.md 冻结候选、独立出题与复核、外部保管和一次性登记。仅去重题干或只跑一次都不能证明独立性；
4. 桩（scripted）跑出的数字必须标注 `provider=scripted`，不得与模型数字混排；
5. 实测报告随代码与数据版本交付；命令可重建评估过程，真实模型允许采样波动。目标数值与历史未核验数字不作实测结论。

| 类别 | 约束 | 违反判定 |
| --- | --- | --- |
| 依赖 | 仅 `fastapi` / `uvicorn` / `pydantic` / `httpx` / `pytest` | 出现其它运行时依赖需评审 |

| ADR-003 | SQLite四表 | Redis / Postgres / 无持久化 | 单机、短事务、SQL可查trace；低运维 | 可并发读，写入需串行；高并发写入需重新选型 |
| ADR-004 | 统一 OpenAI 兼容协议 | 各厂商 SDK | 复用通用协议；切供应商时仍核验工具调用、消息格式、usage、输出限制与错误语义 | 用不到厂商专有能力 |
| ADR-005 | SSE 而非 WebSocket | WebSocket | 服务端单向推送，SSE 更简单、可穿透代理、易调试 | 无法做双向中断（转人工是返回值不是指令） |
| ADR-006 | 单 Agent + 策略层覆写 | 多 Agent（分类/答复/审核） | 本场景无需角色间协商；单链路易追踪，但模型选择仍不确定 | 无法演示"协商"能力（本项目不需要） |
| ADR-007 | 模型只建议、策略层决策 | 完全信任模型输出 | 转人工是合规要求，不能由模型的不确定性决定 | 策略阈值需人工维护 |
| ADR-008 | 先自建数据集 | 公开数据集 | 公开电商售后中文语料难以获取且与本项目字段不匹配 | 数据集规模小、单人标注（已在风险中登记） |

## 14. 术语表

| 术语 | 含义 |
| --- | --- |
| run / 运行 | 一条工单的一次完整处理，对应一个 `run_id` |
| trace | 一次运行的完整记录（会话 + 轮次 + 工具调用），用于回放 |
| 幂等键 | 防止同一 run 内重复执行同一工具调用的键 |
| 折叠 | 把超出窗口的历史轮次压缩成结构化摘要 |
| 降级 | 未能正常完成，但仍返回可用草稿并强制转人工 |
| 桩 / scripted | 不调用模型的确定性假实现，仅用于验证链路与评估工具 |
| 采纳率 | 人工复核为A档的草稿数/已复核数；自动要素检查另报，不视为真实客服采纳 |
