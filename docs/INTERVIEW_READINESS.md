## 2 值得保留的内容

- 场景聚焦：四种意图、有限工具、草稿输出，便于说明边界。
- 工程机制明确：停止条件、工具Schema、策略覆盖、SQLite trace、幂等及回放。
- 有取舍：为何不用编排框架、为何不用RAG、何时再考虑扩展，适合深入追问。
- 有评估意识：分类、工具、参数、草稿分别评价，并区分离线桩与真实模型。

这些是良好的设计起点。评审中应继续追问能否实现和验证，不能把文档完整等同于工程完成。

## 5 推荐完成顺序

1. 按IMPLEMENTATION第2至4章创建合成订单、类型和只读工具，验证订单归属。
2. 完成Provider协议、离线桩与有界循环，先跑通CLI。
3. 实现四表、审计、幂等与trace，确认第二次跑相同用例不会丢记录。
4. 接真实模型，保存每次请求和模型计量；没有Key时继续完成HTTP与SSE。
5. 创建真实的数据文件和评估脚本，产出基线，不预设提升幅度。
6. 针对实际失败修一个问题，用冻结事实重跑并检查其他用例，保存改前改后原始结果。
7. 最后整理演示、证据索引和简历描述，所有数字来自已保存报告。

## 6 面试时如何讲

当前可以这样介绍：

> 我围绕电商售后设计了一个单工单Agent，目标是意图分类、查询订单和生成回复草稿。我重点约束了工具访问、不可逆操作、运行预算与回放。当前完成的是文档设计，代码和真实模型评估还在后续开发范围，因此没有把目标数字作为实测结果。

实现完成后，用自己的实际事实替换以下占位内容：

> 我实现了[实际组件]，通过[具体命令]演示[具体工单]。一次评估发现[现象]，trace定位到[代码和原因]；改动后在[数据版本/样本数]上验证[实际变化]。当前限制包括[合成数据/单机/未接真实电商]。

不要直接复用“参数正确率87.5%降到4.2%”作为个人经历，除非能解释并提供对应实现、原始报告和修复证据。
不要把模型选择工具的有界循环说成纯确定性流程，也不要把仅有规则路由的离线桩说成真实Agent推理。

## 7 常见追问与需要准备的证据

| 问题 | 回答应落到哪里 |
| --- | --- |
| 这个场景为什么要Agent，普通工作流不行吗 | 用规则基线对比模型处理模糊诉求的收益；如果没有收益，应承认工作流足够 |
| 为什么没用LangGraph | 当前单链路、有限工具；用代码解释停止和trace，不泛化说框架不好 |
| 模型什么时候能调用退款工具 | 只能命中拦截演示，首版不存在真实退款执行路径 |
| 模型传别人订单号会怎样 | user_id来自受信上下文，工具统一授权检查；本地入口无生产认证须说明 |
| 6000 token怎么严格卡住 | 说明请求前估计、输出额度、响应usage和供应商差异，不承诺精确上界 |
| 你说可回放，为什么两次结果不同 | 区分历史trace、冻结工具事实和真实模型采样 |
| 窗口和步数为何都设为6 | 步数与消息轮数是不同计数；用注入8轮的单测验证折叠，生产路径是否触发需观测，不预设 |
| 全转人工为什么不安全又高分 | 分开看漏转、误转、自动草稿覆盖率和动作阻断 |
| 24条能说明什么 | 只说明固定回归矩阵，不代表线上分布覆盖或泛化结论 |
| 自动要素齐全为何还要人工评分 | 要素齐全不保证金额正确、语义得体、无越权承诺 |
| SQLite如何处理并发请求 | 短事务、活动工单唯一索引、写锁及进程边界，网络调用不占写事务 |
| 真实API失败但没usage，成本怎么算 | 计量缺失单列，不把失败成本记0 |
| Key、手机号和地址在哪里 | 环境变量与统一脱敏；合成数据用于回放，不公开真实个人信息 |
| 哪个难点是你自己解决的 | 展示本人改动、trace和回归记录，不能只背文档故事 |
